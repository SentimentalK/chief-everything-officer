# Journal Rule

`JOURNAL.md` 保存用户时间序列上独特、无法从外部重新查回的个人信号：做过什么、发生了什么、当时是什么状态、有什么体验或情绪、产生了什么兴趣、做了什么决定，以及哪些事情后来重复、持续或发生变化。

它的价值不只是“记住一件大事”，而是让未来的 AI 能把当前问题放回时间上下文。例如用户今天再次提到某个身体不适、情绪状态或行为变化时，Journal 可以帮助判断几天前是否已经出现过、是不是持续发生、最近还有哪些相关事件。它记录观察到的时间事实，为后续判断提供 clue，而不是替用户解释原因。

Journal 不是系统 log，也不是 Task 的历史副本。代码修改、文件重命名、普通 Git commit、项目参数、研究过程、执行清单、价格列表、申请材料细节和其他已经有 canonical owner 的内容不在这里展开。

## 写入

记录有未来上下文价值的用户 episode，不要求一定是重大事件。一次明显的行为、状态、情绪、好奇心、生活变化、实际行动或项目里程碑都可以值得记录；关键是它属于这个用户，并且未来再次出现相关问题时可能有帮助。

只保留理解 episode 所需的最小上下文：什么时候发生了什么、用户当时的状态或体验，以及是否出现了明显变化。详情如果已经属于 Task、Personal 或其他 source，就留在原 owner；Journal 不复制维护。

项目相关内容只有在它体现用户实际做了什么、完成了什么、经历了什么，或方向发生明显变化时才进入 Journal。普通设计讨论和实现细节留在 Task / Git。

Journal 是 append-only。已经写下的历史记录不回写、不删除；如果后来得到新的事实、修正或解释，新增一条 follow-up entry，并注明它补充或修正的是哪次旧事件。

信息不完整也可以先记录，但只能写当前真正知道的部分。不要因为一个事件“看起来应该还有这些细节”就自动补齐严重程度、地点、结果、原因或影响；未知就保持未知。

用户的主观体验可以如实记录。AI 自己的解释如果确实有长期价值，必须明确标成推断或待验证理解，不能把单次行为直接解释成人格、心理状态或因果结论。

如果一个 episode 同时改变了当前长期状态，例如结婚、搬家、换工作或获得新的资产，Journal 保留“这件事发生了”，相应 `personal/` 文件维护“用户现在是什么状态”；两者语义不同，不是重复 truth。
