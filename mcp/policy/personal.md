# Personal Data Rule

`personal/` 保存关于用户本人的长期状态与背景。它贯穿整个 workspace：任何 Task、规划或讨论需要了解用户是谁、过去发生过什么、偏好什么、拥有什么或通常如何判断时，都可以按需读取这里。

长期个人信息优先直接维护在 `personal/`，不要先复制进某个 Task 再把 Task 当成事实来源。Task 只保存当前事项自己的工作状态和局部上下文。

## 文件与发现

每个文件围绕一个清晰、可复用的主题存在，并使用能说明内容的文件名。顶部保留简短 discovery header：

```markdown
# [标题]

- Purpose: 这个文件为什么存在。
- Read when: 什么情况下未来的 AI 应该读它。
- Contains: 里面主要有什么。
```

不维护额外的全局 personal index；需要背景时先看文件名和这些顶部描述，再读取真正相关的正文。

## 写入

只记录用户独特、未来可能复用的信息。公开常识和外部世界本身不属于 Personal；用户与这些事物之间的经历、选择、评价和长期关系才可能属于。

事实、主观体验和 AI 推断必须保持边界。用户明确提供或可靠核验的内容可以作为事实；主观感受保留为体验；AI 的归纳如果值得保存，要明确它仍是推断或待验证理解。信息不知道就保持未知，不为了格式完整而补全。

Personal 允许不完整。缺失的信息如果对当前记录很重要、用户现在很容易回答，可以简短追问；如果不重要、难以取得或用户暂时不知道，就先保存已知部分，后续再补。

如果未来实际使用 `personal/` 时再次需要某个仍为空、未知或未核验的数据，这本身就是它可能重要的证据。尤其当同一缺口重复影响多个任务或第二次以上被需要时，应明确提醒用户这个字段已经成为真实 retrieval friction，并建议现在补全；如果资料难拿、需要查旧文件或不适合当场处理，可以建议建立或更新一个 backfill Task，而不是继续无限期忽略。

长期状态会变化。新信息不要无声覆盖旧历史；在有价值时保留“过去是什么、后来发生了什么、现在如何理解”。对于会随外部条件改变的偏好，记录稳定的条件与偏好变化关系，而不是把某一刻的状态写成永恒人格。

一次观察只有在它有助于未来理解用户时才值得进入 Personal。可以记录发生了什么、用户如何评价、以及它是否改变或加强了某个长期理解；如果只是一个值得记住的孤立事件，更适合 `JOURNAL.md`。

不同 personal 文件可以有不同正文结构，不要求所有个人数据服从同一个 schema。
